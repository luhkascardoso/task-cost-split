Três caminhos possíveis. **Nada configurado ainda**, e a escolha está em aberto ([decisões pendentes](../10-e2e-maestro.md#decisões-pendentes-suas)).

| Opção | Como funciona | Prós | Contras |
|---|---|---|---|
| **EAS Workflows** | Um job `build` gera o app e um job `maestro` roda os flows nos simuladores/emuladores da Expo | Integrado ao Expo/EAS (o projeto já usa CNG). Não precisa de Mac no CI. | Consome créditos/minutos do plano EAS |
| **Maestro Cloud** | `maestro cloud --app-file … --flows …` sobe o binário e roda na infra do Maestro | Paralelismo, relatórios, retries, notificações (Slack/e-mail) | Serviço pago à parte |
| **GitHub Actions + emulador** | Runner com emulador Android (e macOS para iOS) rodando `maestro test` | Sem serviço extra | Mais lento e frágil. Runner macOS é caro. |

**Recomendação:** começar com **EAS Workflows**, só **Android** e só a tag `smoke` em PR. Adicionar iOS e a suíte completa depois.

## EAS Workflows

### 1. Perfil de build (`eas.json`)

```json
{
  "build": {
    "e2e-test": {
      "withoutCredentials": true,
      "ios": { "simulator": true },
      "android": { "buildType": "apk" }
    }
  }
}
```

### 2. Workflow (`.eas/workflows/e2e-test-android.yml`)

```yaml
name: e2e-test-android

on:
  pull_request:
    branches: ['*']

jobs:
  build_android_for_e2e:
    type: build
    params:
      platform: android
      profile: e2e-test

  maestro_test:
    needs: [build_android_for_e2e]
    type: maestro
    params:
      build_id: ${{ needs.build_android_for_e2e.outputs.build_id }}
      flow_path: ['.maestro/flows/auth/sign-up.yaml', '.maestro/flows/expenses/create-and-pay.yaml']
```

- Para iOS é igual, com `platform: ios` (o perfil gera um `.app` de simulador).
- `flow_path` lista arquivos. Comece pelos flows `smoke`.
- Execução manual: `npx eas-cli@latest workflow:run .eas/workflows/e2e-test-android.yml`.
- Para outras opções do job `maestro` (tags, relatórios, retries), consulte a página [Maestro em EAS Workflows](https://docs.maestro.dev/maestro-cloud/ci-cd-integration/expo-eas) e a doc do EAS.

## Maestro Cloud

```bash
maestro cloud --app-file build/app.apk --flows .maestro/ --include-tags=smoke
```

- Opções úteis: `--device-model`, `--device-os`, `--device-locale pt_BR`, `--format junit --output report.xml`, `--async` e `--name`.
- Segredos (ex.: futuras credenciais de backend) ficam em *Manage secrets* no Cloud, nunca no YAML.
- `platform.*.disableAnimations: true` no `config.yaml` só tem efeito aqui.
- Há integração pronta com GitHub Actions, Bitrise, CircleCI e Bitbucket ([CI/CD integration](https://docs.maestro.dev/maestro-cloud/ci-cd-integration)).

## Boas práticas no CI

- Em PR, rode **apenas `smoke`**. A suíte completa vai num agendamento (nightly) ou antes de releases.
- Publique o relatório JUnit (`--format junit`) e os artefatos de falha (prints + hierarquia).
- Um flow instável é um bug: corrija o seletor ou a espera em vez de aumentar retries indefinidamente.
- Mantenha o build de E2E o mais próximo possível do de produção (release, mesma fonte de dados).
